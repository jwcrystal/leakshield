# Agent Transparent Pseudonymization — OpenCode V2

Status: Specification approved for publication. The implementation is on branch `feat/22-transparent-pseudonymization` and has been verified on OpenCode v2.0.28 against synthetic loopback providers (HTTP, WebSocket, AI SDK, hook-only and wire modes) and, for the long-history fork, once against a real OpenAI model on 2026-10-14; see the [evidence index](../evidence/README.md). **Not yet verified:** OS keychain key custody on a real host, a real Anthropic Messages provider, other providers' long-history replay, and long-running soak. The Revision Log supersedes older requirements below where it says so; the 2026-10-06b refusal policy and later revisions differ in places from the contract recorded in #21.

## Revision Log

### 2026-10-14 (owner-requested — provider-opaque reasoning state integrity)

1. Provider-authenticated state is replayed byte-for-byte: an assistant message's reasoning/compaction `encrypted`, and `providerMetadata.<provider>.{reasoningEncryptedContent, encryptedContent, signature, redactedData, thoughtSignature}`. Scanning it rewrote bytes the provider authenticates when a detector matched inside the base64 and the replay failed with `invalid_encrypted_content`.
2. The exemption needs both position (assistant message only) and shape (a single base64/base64url run whose decoded bytes are at most 75% printable, so readable or merely base64-encoded text is still scanned). Reasoning `text` and every other leaf are masked as before; a placeholder that moves or disappears during the transaction refuses the request.
3. The wire remaskers already preserved Responses `encrypted_content`; this aligns the session-hook layer. Anthropic `signature` is verified over the thinking text, so masking that text can still invalidate it; this is not changed.

Implementation/evidence: [capacity and lifecycle retest](../evidence/2026-10-14-live-capacity-and-lifecycle-retest.md), regression `tests/opencode-transparent-opaque-state.test.ts`.

### 2026-10-14 (owner-requested — bounded history capacity and explicit deletion reclamation)

1. Transparent guard operations use a documented combined input/output budget of 8 Mi UTF-16 units and 100,000 JSON value nodes, calibrated against the existing 4 MiB HTTP-body/WS-frame limits. Standalone core defaults, per-string scanner bounds, depth and aggregate mapping-entry/byte caps remain unchanged. Exceeding a limit still refuses atomically; no raw-content fallback or unbounded scanning is introduced.
2. Align the guard's core mapping-session ceiling with its existing 4,096 tracked-session cap. Do not evict live mappings to make room. Reclaim session RAM, prepared HTTP scopes and WS lanes only upon the public V2 `session.deleted` event; idle/completion/interruption are not erasure signals. Abort the subscription on plugin disposal. An unavailable stream preserves safe bounded retention rather than evicting sessions or disabling protection.
3. Session deletion is not a durable `forget`: persisted encrypted rows retain their TTL/explicit-erasure policy. Local regressions cover the previously failing large-history and 129th-session cases, including retained tool mappings and atomic over-budget refusal. They do not prove the original real-provider history fork, complete runtime deletion delivery or indefinite host stability.

Implementation/evidence: [capacity verification](../evidence/2026-10-14-transparent-capacity-verification.md). This narrows prior disposal-only in-memory lifetime descriptions without changing persistence opt-ins, wire defaults, attachment policies or tool safety.

### 2026-10-11 (owner-approved — pure hook-only replaces scoped outbound admission)

1. Explicit `wireProtection: false` registers no HTTP request, WS handshake/send, or AI SDK admission hooks and does not transform provider transport settings. There is no SG transport-metadata scan, route/proof refusal, injected-fetch requirement or final-body enforcement. Content protection and the local tool gate remain active. Omission and true retain wire protection.
2. HTTP response and WS receive hooks are optional best-effort display restoration, not outbound enforcement. Successful preparation for the host's session/named-kind/model selects the mapping. Unknown protocols or unverified scopes remain literal. WS restoration starts with response.created and keeps response/channel/buffer isolation, without requiring outbound registrations. A reply-hook registration failure must not remove input/tool protection in hook-only mode.
3. Failed initialization respects the selected layer: hook-only refuses content/tool dispatch without adding transport hooks; wire mode retains the full fail-closed fallback. Input masking failures still stop the affected model call, now carrying controlled reason/stage metadata rather than raw exceptions or content. No raw-content fallback, new persistence, Keychain use or global enablement is authorized by this revision.

This revision supersedes the prior scoped-outbound-admission requirement for false. Evidence: [pure hook-only verification](../evidence/2026-10-11-pure-hook-only-verification.md). The historical conversation's preparation refusal remains a separate diagnosis unless re-run against the actual dispatch snapshot; local hook-contract tests are not proof it is fixed.

### 2026-10-11 (owner-approved — experience-first ingress and scoped compatibility)

1. **Ingress restoration is fail-soft in both wire levels.** A missing/mismatched HTTP or WS request attribution, unsupported reply envelope, SG restoration error or parser-budget exhaustion stops SG rewriting rather than failing a healthy host response. Do not guess mappings, change routing, or restore through another session/kind/model. HTTP SSE retains bounded undelivered original events, replays only those on degradation, then bypasses rewriting; upstream errors, immediate provider error events and consumer cancellation remain real failures. WS retains its one-frame/no-connection-ID limitations, not HTTP-style arbitrary replay.
2. **Explicit `wireProtection: false` expands to conditional compatibility mode.** No final body scan; an unknown observed HTTP/WS route may use hook-only coverage only after successful preparation for the same session, named request-kind hook and provider/model ID. Failed preparation or a model switch invalidates that proof. Metadata checks remain; unknown dialects get no response adapter. SDK initialization is not request attribution, and missing/unsafe injected fetch remains refused because no request-scoped proof exists at initialization. True continues refusing unknown observed routes and validating/remasking supported final bodies. No provider-brand/URL allowlist, no process-wide network-firewall claim.
3. **Tool safety and opt-ins do not change.** Unknown write/execute mappings, unsafe shell restoration and non-atomic mutation still refuse the affected invocation. Attachments, persistence and Keychain are not enabled by experience mode. Omitted wire remains true; plugin mode remains block. Large-content segmentation, complete encoded-span masking and new tool adapters are follow-up proposals, not shipped behavior.

This revision supersedes the older ingress-interruption and unconditional unknown-route requirements below only in the stated scopes. Implementation/evidence: [experience-first verification](../evidence/2026-10-11-experience-first-verification.md). Local host fault injection locks down the refusal symptom but does not establish the cause of the user's real WS lifecycle failure, or authorize global reinstallation/service restart.

### 2026-10-07 (owner-approved — DB-backed persistence replaces the T2 direction; SGP2 format landed)

1. **Persistent encrypted mapping store replaces the deterministic-AEAD direction (item 3 of 2026-10-06b); trigger confirmed, direction changed.** The real-world annoyance trigger for resumed sessions showing literal placeholders was confirmed by the owner on 2026-10-07. Instead of deterministic reversible tokens, cross-restart restoration is provided by an opt-in encrypted SQLite mapping store: per-session isolation (US7) is retained and persisted; restoration remains a mapping lookup, never a reinterpretation of SGP1/SGP2 tokens as ciphertext. When enabled (`persistence.enabled`, transparent mode only), US8 (process-memory-only) and the single-process framing of US9 are replaced by dual-secret custody — the mapping file is encrypted per entry with a key held in the OS keychain (ladder: OS keychain → explicit 0600 keyfile → memory-only degrade), and both secrets together are required to re-identify; bounded retention (TTL, default 7 days, plus explicit `forget`) replaces process death as the lifetime boundary. Key disclosure alone or DB-file disclosure alone exposes nothing retained; backups of the DB file are a documented residual risk that forget cannot reclaim. When the store or keychain is unavailable the guard degrades per-process to memory-only operation (store) or one-way behavior paths per item 1 of 2026-10-06b (missing mappings) — never fail-closed on a conversation. Deterministic same-original-same-token behavior across sessions is explicitly rejected as a default; a cross-session stable-ID option is deferred and, if ever built, must be opt-in. `--doctor` surfaces persistence status (OFF / OK with store path, session count, TTL, key source / DEGRADED with reason); `forget` output is content-free (counts only). With persistence disabled (the default), every existing requirement, guarantee, and test outcome is unchanged. Recorded in `docs/plans/2026-10-07-persistence-decision-db-over-t2.md` (§10 adds the pre-build survey: none of the four reference integrations ships a key provider; mainstream custody is cloud-KMS/BYO).
2. **SGP2 typed token format landed (item 6 of 2026-10-06b, W1).** New mints are `[SGP2:<FINDING_TYPE>-<seg>-<seg>-<seg>]` — category label from the scanner FindingType (union-merged overlaps keep the highest-severity label), letter-only 4-4-4 payload (digit-free by construction, hex-like runs capped at 4, ≈56.6 bits). The category/payload separator is `-`, not the illustrative `:` of the T3 sketch: a colon would make every SECRET/ENV_SECRET token self-match the built-in generic-secret keyword rule. SGP1 remains a recognized shape whose mappings restore exactly when present (including hydrated pre-upgrade mappings); tokens without mappings follow item 1 of 2026-10-06b. Corpus measurement (1020 tokens across detector families): 0.000% built-in hit rate under default and URL-enabled profiles, versus a 0.294% `phone-tw` baseline for SGP1 — evidence `docs/evidence/2026-10-07-sgp2-fp-corpus.md`, which also records the same-day implementation of item 2's telephone opt-in and reaffirms that sampling-zero is not immunity to custom rules or known values.
3. **Core purity and hydration seam.** The pseudonymization core remains fs/db-free; persistence integrates through a seed/hydration interface (`seedSession`: all-or-nothing, both token versions, full budget checks) and a read-only export — storage, key providers, TTL sweeps, and forget live in adapter modules.
4. **Store integrity invariants (adversarial review round, same day).** The persisted store is opened through a lazily loaded driver (a runtime without `node:sqlite` degrades to memory-only even for users who never enabled persistence). Key identity is pinned in store metadata (a digest of the key): a resolved key that does not match refuses to open — memory-only degradation, never silent re-keying. Writes are guarded by optimistic concurrency: the row version observed at hydration time must still hold at write time (a stale second writer is refused, a vanished row with a remembered version is a conflict), and a store-wide forget epoch makes writes from pre-forget handles fail instead of resurrecting erased data. Retention is bounded by TTL plus LRU caps (default 256 sessions / 50,000 entries). Erasure is logical plus in-file best effort (`secure_delete`, post-forget vacuum and WAL truncation); physical-media and backup residue are documented residual risk, and `forget` output remains content-free. Seed intake validates the SGP2 category against the closed FindingType enumeration and judges size caps before any allocation. Row versions follow a monotonic lineage across deletes (tombstones): a re-created session continues numbering, expected-version 0 is the dedicated absent sentinel, initialization and key pinning run in one immediate transaction with never-replacing metadata inserts, probe handles never initialize or pin (and `forget --all` deliberately clears the pin as the reset path), and a single snapshot larger than the entry cap is refused outright. Row versions are allocated from a global monotonic counter (never reused), absent looks carry the session's tombstone generation as a compare-and-swap token, the tombstone table is bounded with documented pruning semantics, per-session guard bookkeeping is bounded while live sessions retain their tokens, keychain values that are present-but-empty are treated as corruption (never silently re-keyed), a non-empty legacy store is AEAD-verified before its key identity is pinned, and WAL / secure-delete / bounded lock-wait are per-handle settings pinned by direct assertions.

### 2026-10-06b (owner-approved)

1. **Refusal reclassified: tolerate parse uncertainty only when protection and input integrity remain provable.**
   - Unresolvable reserved markers (orphaned, foreign, expired, malformed, bare-prefix, or split) do not by themselves justify refusing a provider-bound request or history replay. A prefix or matching format grants no ownership or scan exemption: only tokens registered to the requesting session, or cryptographically verified tokens after item 3 is implemented, qualify. Unverified content is still scanned, including marker payloads. Preserve literal content only when no sensitive originals are detected; if a complete unowned marker contains a finding, mask the whole marker instead of nesting a replacement inside it. Malformed, bare-prefix, and split content is scanned as ordinary text; an absent terminator must not exempt subsequent text. Findings crossing marker boundaries require full coverage or safe refusal.
   - Apply the same rule to structural identifiers, transport metadata, and numeric positions: preserve unresolved markers only when no sensitive originals are exposed; refuse detected sensitive content that cannot be masked or renamed without breaking the protocol. Existing fail-closed safeguards for unsupported routes, scan limits, scanner errors, and unscannable input remain. Mapping loss alone never blocks history replay. Degradation surfaces through available local conversation/tool diagnostics and a content-free host-log WARN — no provider-body notices or side files; `--doctor` does not promise degradation-history queries.
   - Every remaining refusal carries an actionable, content-free message naming the cause (detector/rule, position kind) and the remedy. Known-unsupported routes (WebSocket, `aisdk`, unrecognized dialects) are surfaced pre-flight by `status`/`--doctor` rather than first hit mid-conversation, and degradation notices never enter provider-bound bodies.
   - Tool-side degradation is permitted only for proven read-only calls whose targets and argument semantics remain safe with literal placeholders. Side-effecting calls (including writes, deletes, or outbound transmission) and unsupported shell contexts are refused when correct restoration or safe semantics cannot be guaranteed. Restoration policy is per field, not per tool (amended 2026-11-05): shell tools and command-like fields get shell rules, `code`/`script` fields restore a placeholder only under a restricted single-line string rule (a conservative heuristic, not syntax verification; it can over-refuse and miss, refuses multi-line strings, triple-quote lines and backslash continuations, and guards the restoration context only, not egress) and refuse originals containing shell-unsafe characters; a refused call is blocked, not masked, and keeps its placeholder, and all other fields of unknown tools restore verbatim. The built-in `execute` (Code Mode) tool's source is not restored: placeholders are restored when the code calls a tool, under that tool's field rules, and a placeholder in the source stays literal. `execute` source holding a mapped placeholder together with `fetch` is refused, so that a failed call cannot be read as a verdict on the value; this is a text match, not a network control, so other spellings are not caught and then send only the placeholder. JavaScript computing on a placeholder (length, encoding) sees the placeholder and gets no error. The restricted single-line rule still applies to the `code`/`script` fields of other tools. A value recognisably derived from a placeholder of this session but with its format changed (brackets dropped, separators or case altered) is refused rather than passed on; a partially masked value, or one the model replaced entirely, cannot be detected and reaches the tool as written. Verified on OpenCode v2.2.5 only. Validate the entire invocation before applying replacements or allowing side effects; retain shell quoting/globbing/option-injection and input-shape safeguards. Refuse only the affected invocation, not the session, and provide actionable, content-free diagnostics in-band and in the host log. Correctly restored originals remain subject to existing OpenCode permissions; no separate authorization system is added.
   - Resolve valid overlapping findings by masking their union, including transitively overlapping spans; containment uses the outer span and identical spans are deduplicated. The output must be non-overlapping and cover every actionable finding, with rescan and original-absence checks retained. Do not discard partially overlapping tails by selecting only the longest span. Invalid coordinates or conflicts with registered-token restoration integrity remain grounds for safe refusal.
   - This item narrows the request failure contract only for unresolved markers that can be safely protected, and the tool failure contract only for proven-safe read-only literal-placeholder calls. "No notice-substituted continuation" remains required for unprotectable input; "tool was not executed" and no-side-effect assertions remain required for unsafe restoration. Tests identify these cases by behavior, not stale spec line numbers.

The numeric-field scan is retained but bounded to content positions instead of every numeric value. Implementation is triggered only if resumed sessions showing literal placeholders become a real-world annoyance. The three examined reference integrations do not establish cross-restart restoration for this project. Use a distinct format version for ciphertext, coordinated with item 6; old tokens with valid mappings remain restorable, and tokens without mappings follow item 1. ## Problem Statement

Sensitive Guard protects model-bound content today, but blocking or irreversible replacement can interrupt an agent's work. Users need the agent to distinguish sensitive records, use original values in permitted local tools, and present readable results without routinely sending detected sensitive values to an LLM provider.

The approved email de-identification trial deliberately retained no reverse mapping and kept block as the default. It is not sufficient for this workflow and must not be retroactively described as reversible.

The target user is one person running OpenCode locally, potentially with multiple sessions, using either the OpenCode TUI or OpenChamber. The primary goal is continued normal work after installation, not a new sandbox or a separate authorization system for every use of an original value.

## Solution

Introduce transparent **pseudonymization** for the OpenCode V2 plugin: replace detected sensitive values with stable opaque placeholders before supported model requests, retain session-scoped reverse mappings in memory, and automatically restore known placeholders for tool execution and supported local presentation paths.

Users continue to read original values and use ordinary OpenCode tool permissions. Local history, logs, exports, and generated files may contain originals; the product does not promise that plaintext never reaches disk. Each subsequent model request must be protected again regardless of what the local history contains.

The detector policy is layered. Common credentials, known secrets, and supported structured PII are enabled by default. Broad, ambiguous categories are not indiscriminately replaced. Local NER is optional and requires separate model provisioning; its declared Chinese and English capabilities must be independently evaluated.

New installations should use transparent mode by default. Existing explicit block/redact settings remain effective, and existing implicit defaults require an explicit migration path rather than a silent change to credential restoration.

## Implementation Decisions

### Scope and trust boundary

- Target OpenCode V2 and both the OpenCode TUI and OpenChamber for the first release. Do not infer V1 support from an existing compatibility entrypoint; preserve its established behavior and document support separately.
- Cover both PII and credentials in transparent mode. The local reporting workflow is an acceptance example, not an exclusive allowlist of supported tools.
- Protect detected values in supported provider-bound requests. This is not a claim that every sensitive value can be detected.
- Accept local originals in chat history, outputs, files, and logs. Memory-only mappings do not imply plaintext never reaches disk.
- Retain existing OpenCode tool permissions. Do not introduce per-export approval, tool/argument/destination authorization policies, or a mandatory manual reveal UI.
- Do not promise control over arbitrary tool network egress, direct access to source files/environment variables, or malicious local clients. A permitted tool may use or transmit originals.

### Modes, migration, and compatibility

- Add transparent pseudonymization as a distinct mode rather than silently changing the semantics of irreversible redact or de-identify.
- Keep the existing email de-identification trial irreversible; it remains a separate feature and historical specification.
- Make transparent mode the new-install default. Preserve explicit legacy policies. Distinguish existing implicit-default installations before changing their behavior; define and test a practical migration mechanism before releasing the new default. *(Deferred: see the 2026-10-06 revision item 2.)*
- If reliable new-versus-existing-install detection cannot be established, require explicit adoption for ambiguous installations. Do not silently treat every omitted mode as consent to credential restoration.
- Keep agent detector defaults separate from global scanner defaults so that CLI, CI, and Web behavior is unchanged.

### Hooks and capability gates

- Use OpenCode lifecycle hooks to protect assembled model requests, restore tool inputs before execution, and restore responses/tool results along proven local delivery paths.
- Manage mapping lifetime explicitly. Hook registration does not establish session-end detection, durable resume, eviction safety, or response persistence semantics.
- Verify the installed runtime and plugin API, event ordering, supported response transports, and mutation semantics before choosing concrete restoration hooks.
- A provider HTTP-response hook is not a generic client-display hook. Do not claim it restores assistant text for both UIs solely because it exists.
- Provider HTTP streaming and WebSocket transport are distinct. Enumerate and prove supported routes; do not enable an unprotected route under a blanket model-boundary guarantee.
- Prefer one server-side integration for both clients if runtime evidence supports it. Client adaptation is permitted if necessary for automatic presentation, but strict display-only isolation is not required. Avoid unrelated client changes.
- Every supported provider-bound request must be protected, including tool-driven continuations, restored local history, title, compaction, and auxiliary generation. Reuse the current strict boundary behavior for scan truncation, encoded content, and unscannable input rather than forwarding unchecked content. **2026-10-05 revision (owner-approved)**: unsupported attachments are no longer a hard refusal in transparent mode — media/file parts are replaced with an omission-notice text part (strip-and-notify, the mainstream DLP action); binary content still never crosses the boundary, and non-part-slot attachment shapes still fail closed. *(Amended by the 2026-10-06 revision item 1: the never-crosses rule applies to the default `block` policy; `allow` is scan-free by explicit configuration.)*
- In-text ignore directives must not disable model-boundary protection. Verify the actual request after interaction with other plugins; plugin ordering is part of the compatibility evidence.

### Mapping and restoration

- Maintain a bidirectional mapping in memory, scoped to the actual OpenCode session identity. Do not add SQLite or another persistent mapping store in this release.
- Use stable opaque placeholders for repeated values in a live session and keep distinct originals distinguishable. Preserve exact originals for restoration; do not inherit normalization that can destroy distinctions merely because it was acceptable in the irreversible email trial.
- Restore only registered placeholders from the requesting session. Do not infer an original from a placeholder's spelling or from another session's mapping.
- Reuse issued-placeholder recognition for unresolved-token detection. A foreign or expired placeholder requiring restoration must not be accepted as a real value; proven-safe read-only literal use follows the 2026-10-06b revision item 1 and is not restoration.
- In model-bound content and assistant display text, unknown or malformed reserved markers grant no ownership. Scan unverified marker payloads and surrounding text; preserve literal content only when safe, and mask a complete unowned marker as a whole when its payload contains sensitive findings. Structural identifiers and metadata still refuse sensitive content that cannot be safely protected; tools retain input-integrity safeguards. See the 2026-10-06b revision item 1.
- Cover supported nested tool inputs and key/value structures without silently creating key collisions or changing types.
- Preserve shell and tool argument semantics. Naive substitution inside shell syntax is not accepted as proof of safe restoration; define a supported restoration strategy, test quotes/newlines/metacharacters, and stop the affected operation when correct restoration cannot be guaranteed. This is input integrity, not a new destination-approval system.
- Retain active mappings without a short fixed TTL. Use explicit clearing/session disposal where supported and process shutdown as known lifetime boundaries. Treat archival, idleness, and actual task completion as different states; do not infer safe clearing from a transient idle event.
- Set documented per-session and aggregate memory limits. Do not silently evict live mappings. At capacity, fail closed for affected new content while preserving usable existing mappings and unrelated work.
- Restart, explicit clear, or reclamation invalidates the affected memory mappings. Refuse only affected tool operations whose unresolved values prevent safe semantics; proven-safe read-only literal use may degrade visibly. Provide recovery guidance. Rereading a source does not guarantee the old placeholder becomes valid again; refresh affected references/context rather than guessing.
- Initialization, scanning, and mapping errors must not forward affected originals to the provider as a fallback. Do not log reverse-map contents for diagnostics.

### Failure contract agreed with issue #21

- When transparent mode cannot safely protect required model input, stop that affected model request before dispatch. Do not replace the required input with a blocked-content notice and continue reasoning with incomplete data. Successfully pseudonymized sensitive content is not a failure.
- When a tool requires an unresolved mapping or restoration cannot preserve its input semantics, refuse that affected tool invocation before execution and without its side effects. The only literal-placeholder exception is a proven-safe read-only call under the 2026-10-06b revision item 1. Preserve the session and unaffected live mappings; unrelated operations may continue.
- Recovery from mapping loss is manual in this release. Tell the user to provide or reread the source and refresh affected references/arguments. Do not automatically reread sources, reconstruct missing originals, or assume a newly issued placeholder validates an old one.
- A later invocation may proceed when its current parameters can be fully and correctly restored or qualify for proven-safe read-only literal degradation. Identical unsafe unresolved invocations remain refused. Do not create a plugin recovery/retry loop, drop required data to make a retry succeed, or claim to control all agent-level retries.
- Errors identify the safe rule/type identifiers, failure boundary, and actionable recovery steps without originals, finding previews, reverse-map contents, or sensitive dynamic identifiers. Use a generic safe category if no rule applies; this restriction is for guard-generated diagnostics, not a promise that all local logs are plaintext-free.
- Preserve normal notify behavior for existing explicit block mode and its established initialization fail-closed behavior. A general notify/abort blockPolicy remains a separate design task in issue #21 and is not a release prerequisite or added configuration burden for issue #22.
- Stopping one request or invocation is not a guarantee that the entire task/session has terminated. Prove refusal, error propagation, and subsequent behavior with runtime tests. Hook exceptions, provider retry controls, or session interruption APIs are implementation candidates, not evidence of complete agent retry control.

### Detector policy and dependencies

- Default-enable common credential formats, known secrets, email, telephone, and validated supported financial/identity formats. Publish concrete format and region coverage rather than claiming every national identifier is covered. *(Amended by the 2026-10-06 revision item 4.)*
- Prioritize Taiwanese identity/telephone fixtures and common international formats; separately document supported regions. Language coverage is not the same as identifier-region coverage.
- Do not indiscriminately enable generic URL, IP-address, date, organization, or place detection. Explicit sensitive values/custom rules may still protect such content, and credentials embedded inside URLs remain protected.
- Distinguish a contextual date of birth from an ordinary date. An organization's NER label alone does not establish whether its name is confidential.
- Add constrained workspace .env discovery and explicit known values using existing exact-value mechanisms. Define supported filenames, bounded discovery/loading, excluded dependency/generated directories, symlink containment, refresh/invalidation behavior, and short-value handling. Do not scan arbitrary files outside the approved workspace scope. *(Amended by the 2026-10-06 revision item 4.)*
- Reuse current detectors where suitable. Evaluate independently usable Rehydra recognizer/NER capabilities before adding a dependency; do not install a second overlapping OpenCode plugin or commit to the entire SDK without checking its boundaries.
- Review dependency licensing, maintenance, runtime compatibility, resource use, and whether detector APIs can be used without an unwanted parallel mapping pipeline. If unsuitable, evaluate another detector/model rather than automatically building a new NER engine.
- Enable credential detection explicitly if a reused SDK makes it opt-in. Our defaults are product decisions, not the dependency's defaults.
- Make NER optional, using local inference by default. Explain model download, startup, disk, RAM, and inference costs. Model weights need not be committed into the application package.
- Require tested Traditional Chinese, Simplified Chinese, English, and mixed-language coverage for the optional NER capability. Do not claim Chinese names/addresses are automatically covered in the default regex/exact-value profile.
- Report disabled, missing, failed, or unavailable NER accurately. Do not silently present fallback regex coverage as full contextual PII protection. Define a visible degraded-mode policy before release.
- Calibrate category-specific thresholds using evaluation data rather than copying example confidence scores. Overlapping detections must preserve restoration integrity and must not hide credentials under a lower-risk category.

## Testing Decisions

- Test externally observable behavior, not private map layouts, exact helper names, or the mere presence of a registered hook. Stable relationships, restoration outcomes, request contents, and failure behavior are the relevant assertions.
- Use the existing mock-provider boundary E2E harness as the principal seam. It already runs real OpenCode against a capture provider and tests admission, tool replay, ordering, auxiliary requests, and resume. Extend it rather than building a new product test API.
- Keep unit tests for strict ingress protection, mapping behavior, configuration, and detector quality. They complement rather than replace the real provider/client evidence.

### End-to-end acceptance

- Place synthetic canaries in a prompt, a source file, an approved tool response, nested object keys/values, and configured known-secret sources. Capture every supported provider request and assert that the expected originals are absent and appropriate stable placeholders are present.
- Verify the mock provider can return placeholders that a real tool receives as the exact originals. Cover PII and synthetic credentials; never use production secrets in evidence artifacts.
- Verify a local report and an existing-credential task with a local mock service complete using originals. Cover controlled secret-file generation as an additional tool-input/output scenario without external publication.
- Exercise shell quoting, whitespace, newline, Unicode, and metacharacter values. Assert intended arguments and effects, and assert safe refusal when restoration would change syntax or cannot be supported.
- Verify assistant and tool-result presentation in actual OpenCode TUI and OpenChamber clients. Provider capture alone does not prove UI restoration; document tested versions and collect client-specific evidence.
- After restored local presentation/history, continue the conversation and assert that originals remain absent from subsequent provider requests, including title, compaction, auxiliary calls, and resumed-history requests.
- Exercise supported streaming paths and explicitly account for any unsupported transports. A non-streaming success is not evidence for streaming or WebSocket safety.
- Exercise both plugin orderings with a canary-injecting companion plugin. Verify actual request contents or record and enforce a compatibility limitation; do not assume hook order provides complete protection.
- Test same-session resume while mappings are alive and restart resume after mappings are lost as different scenarios. Restart must not produce guessed originals or unsafe literal-placeholder tool actions; proven-safe read-only degradation requires visible diagnostics.
- Keep the no-plugin expected-leak case as evidence of the deployment boundary, not a product failure.
- For unprotectable required input, assert that the affected provider call is not dispatched and that no notice-substituted continuation is used in its place. Attribute captures to the failed operation: unrelated title/auxiliary calls are not evidence that the failed call was dispatched.
- For unsafe or side-effecting unresolved tool restoration, assert that the tool was not executed, its side effects are absent, the error is actionable and contains no synthetic original or preview, and unrelated valid operations remain usable. Separately prove read-only literal degradation preserves target/argument semantics and emits content-free diagnostics; an unresolved placeholder alone is not proof of safety.
- After mapping loss, assert that the plugin does not automatically read sources or retry restoration. A repeated unsafe unresolved call must still have no side effects; a manually refreshed invocation with valid current references may execute normally. Observe any runtime agent retries explicitly without claiming that the plugin terminates the whole session.

### Mapping and configuration acceptance

- Verify repeat stability, different-value distinction, exact restoration, session isolation, forged/foreign/expired placeholders, clearing, restart loss, and bounded capacity behavior.
- Verify existing mappings are not silently evicted at a limit and unrelated operations remain possible after an affected restoration failure.
- Verify model-boundary failures never fall back to raw originals, including unsupported input, scan limits, ignored directives, encoded canaries, and invalid initialization/options.
- Verify nested tool inputs and key collision handling, and ensure diagnostics do not dump originals or map contents.
- Verify valid-overlap unions cover partial tails, containment, equal-length overlaps, and transitive chains; require exact restoration, rescan, and original-absence checks. Test malformed or unterminated markers wrapping synthetic secrets without granting scan exemptions, and preserve valid SGP1 restoration alongside newer token versions.
- Verify default new-install behavior, explicit legacy-policy preservation, implicit-default migration, optional NER availability reporting, and unchanged non-agent defaults.
- Preserve existing block/redact/de-identification regression tests. Do not impose a plaintext-free local-history requirement on transparent mode.
- Keep existing block notify regression cases separate from transparent-mode request refusal. Verify established initialization fail-closed behavior and safe failure diagnostics without adding a generic blockPolicy option.

### Detector and NER acceptance

- Build category- and region-labelled fixtures with positive and negative examples. Report precision and recall separately by type and, for NER, by language; one aggregate score is insufficient.
- Include Traditional Chinese, Simplified Chinese, English, mixed-language text, names/addresses in prose and structured records, and ordinary coding contexts.
- Include public documentation URLs, IP literals, release dates, function names, package names, and public organization names as negative/control fixtures for the selected default policy.
- Test short/common known values, overlapping findings, configured URL secrets, .env changes, symlink escapes, excluded directories, loading limits, and exact-value refresh behavior.
- Define dataset-specific release thresholds before implementation sign-off. Require zero original-canary occurrences in the covered provider-boundary scenarios; do not extrapolate that result into universal detection completeness.
- Measure startup, warm/cold inference latency, peak memory, and model provisioning for the candidate local NER on documented hardware. Do not treat published SDK example timings as our measured performance.
- Verify NER processing itself does not transmit fixture text to a remote inference service under the default local configuration.

## Out of Scope

- Persistent or encrypted reverse-mapping databases, cross-restart restoration guarantees, and sharing mappings between users or sessions.
- A separate original-value authorization system, per-export approval, destination-aware tool policies, network egress enforcement, or a complete execution sandbox.
- Guarantees that local chat history, logs, caches, clipboard content, screenshots, or generated files never contain originals.
- Mandatory click-to-reveal presentation, strict separation between UI projections and canonical persisted history, or a new standalone reveal dashboard.
- Changing CLI, CI, or Web scanner defaults; replacing or rebranding the approved irreversible email trial.
- Automatic new-feature support for OpenCode V1, other agent runtimes, shared multi-user services, all languages, or every jurisdiction's identifiers.
- A bespoke NER training pipeline, guaranteed legal anonymization, complete secret detection, or prevention of all tool-based disclosure.
- Automatic source rereading/reconstruction after mapping loss, a plugin-owned recovery retry loop, and the general blockPolicy design deferred to issue #21.
- Unrelated refactoring and overwriting existing uncommitted work.

## Further Notes

- This specification supersedes earlier conversational proposals for mandatory per-operation approval and strict plaintext-free history. Those stronger policies may be considered separately, but are not prerequisites for transparent mode.
- The failure contract for issue #21 follows the 2026-10-06b revision: refuse unprotectable requests and unsafe tool invocations, allow only proven-safe read-only literal degradation, provide safe diagnostics, and require manual mapping recovery. The remaining generic blockPolicy design stays open; do not close issue #21 or treat it as a blocker requiring a new policy option for this release.
- Preserve the domain distinction: **redact** is irreversible replacement, **de-identify** retains stable relationships without a reverse map, and **pseudonymize** retains a reverse map. None establishes legal anonymization.
- Recommended delivery order: (1) runtime/hook and dependency feasibility gates, (2) complete transparent flow using existing detectors, (3) expanded structured/known-value detection, (4) optional local NER and its bilingual evaluation. This is implementation sequencing, not permission to declare the complete scope delivered after the first slice.
- Before release, settle concrete mapping limits, configuration schema, migration mechanics, .env discovery boundaries, NER model selection, quality thresholds, and the supported runtime/transport matrix. These are bounded implementation gates, not claims of already-established APIs or results.
- A ready-for-agent label means the implementation objective and its gates are specified. It does not mean the hooks, dependency suitability, bilingual quality, or dual-client behavior have already passed verification.
- Reference implementations inform mechanisms, not proof of our safety or compatibility: official Rehydra, the EightDoor integration, and the inspected Vibeguard plugin use in-memory mappings in the examined revisions. Rehydra SDK SQLite support does not imply the plugin persists mappings.
- Reference documentation: [Rehydra PII types](https://docs.rehydra.ai/concepts/pii-types), [OpenCode plugin](https://docs.rehydra.ai/guides/opencode-plugin), [NER detection](https://docs.rehydra.ai/guides/ner-detection), [OpenCode V2 plugins](https://opencode.ai/v2/docs/build/plugins).
